# KBC Time Machine POC — Design

**Date:** 2026-09-30
**Sources:** `KBC-Time-Machine-Product-Brief.md`, Tectonic Hackathon Participants Guide (KBC challenge only), `sim-user-data.json` (synthetic data made by `generate_sim_user_data.py`)

## 1. Goal

A working, secure web proof of concept of "KBC Time Machine" that looks like KBC Mobile. It is demoed on a laptop or projector. Every insight is computed from each customer's own transactions, so the same engine personalises for any customer; that answers the challenge's "2.3M customers" question.

The demo covers the brief's two journeys, using the three synthetic profiles in `sim-user-data.json`:

| Login | Profile | What the engine finds (as of 30 Sep 2026) |
| --- | --- | --- |
| `desmet` | BE002 Sophie & Thomas De Smet, family with 3 kids | Groceries €1,420 against a usual €842–€981 → **journey 1: cash-flow scenario**. Healthcare €752 also flagged. Back-to-school costs *not* flagged (seasonal: similar last September). |
| `jean` | BE001 Jean Lambert, pensioner | Saving contributions rose from around €200 to €450 a month → **journey 2: connect to a goal** |
| `lucas` | BE003 Lucas Peeters, student with irregular income | Nothing flagged. Shows that the engine doesn't raise false alarms. |

**Judging:** Creativity, Technical ability ("does it work?"), Fit, Security. Security is an Aikido AI code audit covering business-logic flaws, IDOR, authentication and authorization.

**UI principle:** less is more. Only the screens the two journeys need.

## 2. Non-goals

- Real KBC integration, real customer data, notifications, moving money, borrowing, investment advice.
- LLM-generated text. All wording comes from templates; every amount comes from the engine.
- Automatic categorisation. The dataset is already categorised and flags recurring transactions; customers can correct a category.
- Mobile-native or PWA. It's a desktop browser app that renders a phone-width column.
- Deployment infrastructure. It runs locally; the README says how.

## 3. Stack

- **Backend:** Python 3.12+ (3.13 available), FastAPI, SQLAlchemy 2 (sync) on SQLite, Pydantic v2 + pydantic-settings, argon2-cffi, pytest, httpx (TestClient).
- **Frontend:** Vite 5, React 18, TypeScript, react-router-dom 6. Plain CSS with custom properties. Charts are hand-written SVG (no chart library).
- **Dev:** The Vite dev server proxies `/api` to FastAPI on :8000, so the browser only ever sees one origin. For demo or production, `npm run build` output is served by FastAPI.

## 4. Architecture

```
sim-user-data.json       synthetic dataset (source of truth, regenerated by generate_sim_user_data.py)
backend/app/
  main.py                app factory, security middleware, routers, SPA static serving
  config.py  db.py  models.py  deps.py  schemas.py
  security.py            argon2, session tokens, login rate limiter, origin/CSRF guard, headers
  repo.py                customer-scoped data access: the ONLY place customer data is queried
  services.py            glue: CustomerData → engine calls
  seed.py                imports sim-user-data.json into SQLite, generates demo passwords
  engine/                pure functions, no DB/HTTP imports
    types.py money.py baseline.py detect.py forecast.py goals.py suggestions.py texts.py insights.py
  api/                   auth.py overview.py insights.py goals.py common.py
backend/tests/
frontend/src/            api.ts types.ts format.ts auth.tsx useLoad.ts App.tsx styles.css components/ routes/
```

**Boundaries:**
- `engine/` depends on nothing in the app. It takes plain dataclasses and returns plain dataclasses. It is unit-tested.
- `repo.py` is the only module that queries customer data, and every function takes `customer_id`.
- The API routes are thin: get the customer from the session, load via `repo`, call `services`/`engine`, map to schemas.

## 5. Data model (all money is integer cents)

- `customers(id, username UNIQUE, display_name, password_hash, cash_buffer_cents, data_as_of DATE)`
- `sessions(token_hash PK, customer_id FK, created_at, expires_at)`
- `accounts(id, customer_id FK, external_ref, name, number, type ∈ {current, savings, credit_card}, balance_cents)`
- `transactions(id, customer_id FK, account_id FK, external_ref, booked_on DATE, amount_cents (neg = outflow), counterparty, category, kind, recurring BOOL, category_override NULLABLE)`
  - `kind ∈ {income, expense, refund, internal_transfer}` (from the dataset's `type`)
- `recurring_items(id, customer_id FK, label, category, amount_cents (signed: + into current account, − out), frequency ∈ {monthly, monthly_except, yearly}, months ("5" / "1,2,9"; the active months, empty for monthly), confirmed BOOL)`
- `insight_feedback(id, customer_id FK, insight_key, response, created_at)`, UNIQUE(customer_id, insight_key)
  - `response ∈ {one_off, ongoing, wrong_category, dismissed, goal_created}`
- `goals(id, customer_id FK, kind ∈ {car, home, emergency, other}, name, target_cents, target_date NULLABLE, earmarked_cents, monthly_contribution_cents, created_at)`

**Import rules (`seed.py`):**
- Amounts are converted with `Decimal(str(x)) * 100`, never float maths.
- The username, greeting name and cash buffer come from a small mapping:
  - BE001 → `jean`, "Jean", €1,000
  - BE002 → `desmet`, "Sophie & Thomas", €1,000
  - BE003 → `lucas`, "Lucas", €200
  - Unknown profiles fall back to the lowercased id, the first word of the name, and €500.
- Balances are the last month's `closing_balances_eur`.
- `data_as_of` = the last day of `dataset.period.to`.
- An expense or refund with an unknown category makes the import fail loudly.
- Account numbers shown in the UI are fictitious masked numbers.

## 6. Calculation engine rules

**Analysis month:** the month containing `data_as_of` if `data_as_of` is that month's last day, otherwise the month before, so an incomplete month is never analysed. For the dataset this is September 2026.

**Money rules (from the dataset conventions):**
- `internal_transfer` is never income or spending. This covers savings transfers and credit-card repayments.
- Card purchases are `expense` rows on the card account, so they're counted once.
- Refunds net against their category.

Engine totals must equal the dataset's own `monthly_summary` (this is tested).

**Baseline:** for each spending category, the monthly net spend over the *baseline months*: up to 6 complete months before the analysis month, and at least 3 are required. Usual range = min..max; typical = median.

**Spending-increase detector** (fires when all hold):
- typical > 0
- `this_month > usual_high × 1.2`
- `this_month − typical ≥ €50`
- Seasonal guard: when the same month last year is in the history, `this_month > last_year × 1.2`

Priority = `this_month − typical`. Key: `spend:<category>:<YYYY-MM>`.

**Saving-increase detector** (net transfers into savings accounts per month):
- *Recent* = the last 3 months including the analysis month.
- *Reference* = the same 3 months a year earlier when the history covers them, otherwise the up-to-6 months before the recent window (at least 2 needed).
- Fires when:
  - median(recent) > 0
  - median(recent) − median(reference) ≥ €100
  - every recent month ≥ 1.5 × median(reference)
- Key: `saving:<YYYY-MM>`. Priority = the increase × 3.

**Insight lifecycle:**
- Feedback `dismissed`, `one_off`, `wrong_category` or `goal_created` hides the insight.
- `ongoing` keeps it, marked "Noted".
- Home shows at most 3, by priority.

**Forecast** (current account, 1–3 months after the analysis month):
- **Scheduled lines:** recurring items active in that month. Items are "confirmed" unless their amount varies (e.g. salary), in which case they're estimates. Yearly items only appear in their month.
- **Estimated lines:** for each spending category, the median over the baseline months of its *non-recurring* spend (> 0 only).
- The scenario "continues" adds one estimated line, `−(this_month − typical)`, labelled "Extra <category> spending".
- **Per month:** start balance, lines, net, end balance. **Per scenario:** cumulative net, `min_balance`, `below_buffer`.
- `savings_transfer_may_be_needed` = `below_buffer` AND savings balance > 0. It's never based on a repeat count.
- **Assumptions** (returned with the forecast) and the **coverage note** (always shown): "Based on your KBC accounts only. Cash spending and other banks are not included."

**Goals:**
- `remaining = max(0, target − earmarked)`
- `months_needed = ceil(remaining / monthly)`, or none if monthly = 0
- `estimated_completion = month_of(data_as_of) + months_needed`
- If `target_date` is set: `required_monthly = ceil(remaining / months_until)` and `on_track`.
- **Earmark validation** (server): earmarked ≤ target, and the sum of all goals' earmarks ≤ savings balance.

**Next steps (static, each with a reason, never products that execute anything):**

| Goal | Next steps |
| --- | --- |
| car | savings plan; "Compare car financing (illustrative)" |
| home | "Plan your upfront costs"; "Housing affordability tool", with the note "Goal progress alone doesn't establish mortgage affordability." |
| emergency | automate a transfer; "3 × monthly spending" target |
| other | savings plan |

Every list carries "Terms, eligibility and availability to be verified."

## 7. API (JSON; all but login require a session)

| Method | Path | Notes |
| --- | --- | --- |
| POST | `/api/auth/login` | `{username, password}` → Set-Cookie. Generic error. Rate-limited. |
| POST | `/api/auth/logout` | Deletes the session and clears the cookie |
| GET | `/api/me` | `{display_name}` |
| GET | `/api/overview` | accounts, top 3 insights, coverage note, `as_of` |
| GET | `/api/insights/{key}` | detail: history bars, usual range, transactions, evidence, feedback state |
| POST | `/api/insights/{key}/feedback` | `{response, corrected_category?}` |
| GET | `/api/insights/{key}/scenario?months=1..3` | spending insights only; both scenarios + assumptions |
| GET / POST | `/api/goals` | list (+ available to earmark, suggested monthly) / create (optional `from_insight`) |
| POST | `/api/goals/estimate` | timeline for unsaved values (slider); no persistence |
| GET / PATCH / DELETE | `/api/goals/{id}` | owner-scoped |

## 8. Security design

- **Authentication:**
  - argon2id hashes.
  - An unknown username is still checked against a dummy hash, so timing doesn't reveal which users exist.
  - One generic 401 message.
  - Rate limits: 5 failures per (username, IP) and 20 per IP, per 15 minutes → 429.
- **Sessions:**
  - `secrets.token_urlsafe(32)`; only its SHA-256 is stored.
  - 8h expiry.
  - Cookie `tm_session`: HttpOnly, SameSite=Strict, Path=/, Secure when `COOKIE_SECURE=true`.
  - A new token at every login (any old session from that browser is deleted). Logout deletes the session on the server.
- **Authorization and IDOR:**
  - `customer_id` only ever comes from the session.
  - Every `repo` function filters by it.
  - Not found or not owned → the same 404.
  - Insight keys must match an insight *currently computed* for that customer.
  - Path ids are bounded ints.
- **Business logic:**
  - Pydantic with `extra="forbid"`; enums and patterns for keys and categories.
  - `0 < target ≤ €10,000,000`, `0 ≤ monthly ≤ €100,000`.
  - `target_date` must be after `data_as_of` and within 50 years.
  - Earmark limits (see §6); `months` 1–3.
  - `corrected_category` is required exactly for `wrong_category`, must be a spending category, and must differ from the current one.
  - Saving insights accept only `dismissed` (goals connect via `from_insight`).
  - PATCH rejects `null` for required fields.
  - There are no endpoints that move money.
- **CSRF:** SameSite=Strict, plus middleware that rejects state-changing `/api/` requests unless `Origin` (or `Referer`) is in `ALLOWED_ORIGINS` and `X-Requested-With: fetch` is present.
- **Headers:**
  - CSP `default-src 'self'; img-src 'self' data:; style-src 'self' 'unsafe-inline'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'`
  - `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: same-origin`
  - `Cache-Control: no-store` on `/api/`
- **Other:**
  - OpenAPI docs are off unless `DEBUG=true`.
  - No CORS middleware.
  - Nothing secret is committed; `.env.example` shows the settings.
  - Demo passwords are generated at seed time and printed once, or read from `DEMO_PASSWORD`.

## 9. Screens

KBC Mobile look: a deep-blue top bar, a light-grey page, white rounded cards, cyan accents, and a phone-width column (max 420px) centred on a dark backdrop for the projector. The KBC logo is a placeholder SVG (`frontend/src/assets/logo.svg`) to be replaced by the official asset.

1. **Login.**
2. **Home:**
   - the greeting
   - account cards
   - a "Time Machine" section with ≤3 insight cards and an empty state "Nothing unusual this month."
   - "My goals"
   - the coverage note and "Data up to 30 September 2026"
3. **Insight (spending):**
   - the headline
   - SVG bars for the baseline months + this month, with the usual range shaded
   - One-off / Expected to continue / Category is incorrect (+ category picker) / Dismiss
   - "See the impact"
   - "Why you're seeing this" (expandable)
   - the transactions
4. **Insight (saving):**
   - the headline
   - bars of the last 12 months
   - Car / Home / Emergency fund / Another goal / No thanks
5. **Scenario:**
   - a 1/2/3 month toggle
   - two cards: "If it's a one-off" and "If it continues"
   - a buffer warning only when flagged
   - a month-end balance table
   - per-month "what's included", with confirmed lines solid and estimates italic with a dotted underline, and a legend
   - assumptions (expandable)
6. **Goal create/edit:**
   - the kind
   - name, target, optional date, earmarked (shows what's available)
   - a monthly slider → `/estimate`
   - the result
   - next steps with reasons
   - delete (edit only)
7. **Goals:** cards with a progress bar, remaining amount and ETA.

## 10. Testing

- `engine/`: unit tests for each rule, including the brief's worked example (€150 surplus, €350 → €600 gives −€100 a month and −€300 over 3 months).
- **Import:**
  - engine totals match `monthly_summary` for every profile, month and category
  - the three profiles produce exactly the insights in §1
  - the De Smet forecast numbers
- **Security** (pytest with TestClient):
  - login success and failure, the generic message, the rate limit
  - no cookie or an expired session → 401
  - session rotation
  - CSRF and origin rules, security headers
  - Jean can't read or change De Smet's insight or goal (404)
  - validation rejections, earmark limits
- **Frontend:** `npm run build` (tsc strict + vite) passes, plus a manual/automated smoke test of both journeys through the Vite proxy.
